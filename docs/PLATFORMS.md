# Серверные Linux-платформы

Этот документ описывает точный серверный контракт VPN Installer. Клиентская ОС от него не зависит: пользователь по-прежнему запускает основной интерфейс через `.\vpn.cmd` на Windows или `./vpn.sh` на Linux, а устройства подключаются по `out/<deployment>/client/vless-uri.txt`.

## Поддерживаемая матрица

Все серверы должны использовать архитектуру `x86_64` и init system `systemd`.

| Семейство | Дистрибутив | Версии | Package provider |
| --- | --- | --- | --- |
| DEB | Ubuntu | 22.04, 24.04, 26.04 | `apt` |
| DEB | Debian | 12, 13 | `apt` |
| RPM | AlmaLinux | 9.x, 10.x | DNF4 (`dnf`) |
| RPM | Rocky Linux | 9.x, 10.x | DNF4 (`dnf`) |
| RPM | Fedora | 43, 44 | DNF5 (`dnf5`) |

Производные дистрибутивы не определяются по одному `ID_LIKE`: preflight сверяет точные `ID`, `VERSION_ID`, архитектуру и init system с этой таблицей. Одинаковый формат пакетов сам по себе не означает совместимость.

## Как выбирается provider

Пользователь не выбирает package manager вручную. Перед изменением сервера установщик читает `/etc/os-release`, проверяет архитектуру и `systemd`, после чего создаёт канонический platform descriptor.

Роли описывают логические зависимости, например Python runtime, `nftables`, DNS cache или WireGuard tools. Platform provider один раз преобразует их в реальные имена пакетов:

- `apt` выполняет обновление индекса и установку через `apt-get` без recommended packages;
- DNF4 используется на AlmaLinux и Rocky Linux;
- DNF5 используется на Fedora;
- очистка package cache и `maintain` выполняются тем же provider, который записан в manifest.

Install plan содержит и логические requirements, и разрешённые имена пакетов. На сервере он повторно сверяется с обнаруженной платформой, поэтому пакетный план для одного семейства не применяется к другому.

При установке через SSH platform facts используются и для локального render выбранных узлов. Архив содержит ожидаемый manifest: сервер повторяет render для своей ОС и отклоняет несовпадение до установки пакетов. Смена ОС или входных данных между preflight и установкой требует новой сборки. Переносимый console/cloud-init bundle без выбранного сервера определяет платформу при запуске на целевой машине.

## DNS

VPN Installer использует отдельный app-owned DNS cache на базе `dnsmasq`. Его конфигурация хранится в `/etc/vpn-stack`, а процесс запускается собственным systemd unit проекта.

Границы владения:

- сервис обслуживает только серверный VPN dataplane;
- системный resolver дистрибутива не заменяется;
- `/etc/resolv.conf` не переписывается и не входит в transaction ownership;
- различия версий `systemd-resolved` не влияют на конфигурацию VPN;
- конфигурация и service state app-owned DNS входят в manifest, drift check, acceptance и rollback.

## Firewall

Проект использует `nftables` и владеет только своими именованными таблицами и systemd unit их применения. Он не выполняет глобальный `flush ruleset`, не присваивает себе чужие таблицы и не меняет правила сторонних приложений.

Активные `ufw` и `firewalld` несовместимы с этой моделью владения и должны быть отключены до install/reinstall. Это обязательное предварительное условие, а не автоматическая миграция: установщик не выключает firewall manager и не пытается незаметно объединить два независимых набора правил. Пользовательские правила, добавленные напрямую через `nft`, необходимо заранее проверить на конфликт портов, policy и priority.

## Безопасность хоста

Preflight фиксирует AppArmor или SELinux в platform facts и manifest. Установщик не отключает security module дистрибутива. Все исполняемые файлы, units и конфигурации VPN проверяются как управляемые artifacts; обнаруженная платформа повторно сверяется перед применением install plan.

На SELinux-хостах provider сначала проверяет оба протокола порта `1054` и точные app-owned file contexts. Чужое назначение не перезаписывается. Совпадающие правила сохраняются, отсутствующие добавляются; затем выполняется `restorecon` для файлов релиза. Если эта подготовка завершается ошибкой, удаляются только правила, успешно добавленные в данном вызове. Неудача обратного удаления выводится как отдельная ошибка, а не скрывается.

Успешно созданные SELinux prerequisites остаются на хосте при последующем rollback VPN runtime. Это не полный транзакционный откат host policy. Docker-матрица проверяет пакеты и контракт платформы, но не заменяет испытание на VM с enforcing SELinux; такой полный цикл восстановления пока не подтверждён.

## Подготовка VPS

Перед запуском меню проверь:

1. Установлена точная ОС из матрицы и архитектура `x86_64`.
2. Система загружена с `systemd` и доступен SSH под `root` или через `sudo`.
3. У сервера есть публичный IPv4, а нужные входящие TCP/UDP-порты разрешены у хостинг-провайдера.
4. `ufw` и `firewalld` не активны.
5. На сервере нет вручную созданных правил `nftables`, конфликтующих с портами и policy VPN.

После этого используй интерактивный launcher. Отдельных команд или флагов для выбора дистрибутива нет.

## Future

В будущей работе могут быть отдельно спроектированы:

- openSUSE и Arch Linux: потребуются собственные package providers и отдельная тестовая матрица;
- Alpine Linux и immutable-системы: потребуются другая init/package/filesystem model и отдельный install backend.

Эти направления не входят в текущую матрицу. Для них нет install contract, migration path или проверенной процедуры установки.
