# Сеть сервера и проверка соединения

Если часть сайтов открывается, а часть зависает, сначала нужна проверка пути,
а не смена профиля или таймаутов. Основной VLESS URI и действующий клиент
при такой диагностике менять не требуется.

## IPv6: адрес есть, связи нет

Наличие глобального IPv6 и default route ещё не доказывает доступность сети.
Сервер может одновременно иметь назначенный провайдером статический адрес
и полученный из Router Advertisement адрес SLAAC. Автоматически выбранный
адрес не обязательно разрешён провайдером для исходящего трафика.

Проверка администратора:

1. Посмотреть адреса и выбранный источник: `ip -j -6 address` и
   `ip -6 route get 2606:4700:4700::1111`.
2. Сравнить подключение к тем же двум независимым узлам с обычным выбором
   источника и с явной привязкой к каждому адресу. Не отключать проверку
   сертификатов при проверке доменных сайтов.
3. Если работает только назначенный статический адрес, исправить конфигурацию
   сетевого менеджера. Для Netplan с уже заданными статическими IPv6-адресом
   **и default route** это может означать `accept-ra: false` у нужного интерфейса.
   На сервере, получающем адрес или маршрут через RA, так делать нельзя.
4. До применения проверить сгенерированную конфигурацию: IPv4 и остальные
   интерфейсы не должны измениться. Подготовить независимый откат и проверить
   IPv6 непосредственно с exit, через router и через публичный VPN-вход.

Это исправление конфигурации конкретного хоста, не новая настройка VPN.
Установщик не переписывает Netplan произвольного провайдера автоматически.
Не нужно удалять IPv6 из профилей, сбрасывать conntrack или менять MTU.
IPv6 masquerade тоже выбирает исходный адрес интерфейса, поэтому исправление
выхода важно и для пересылаемого трафика, а не только для самого сервера.

Источники: [Netplan](https://netplan.readthedocs.io/en/stable/netplan-yaml/),
[выбор адреса masquerade в Linux 6.8](https://github.com/torvalds/linux/blob/v6.8/net/netfilter/nf_nat_masquerade.c).

## Сканирование и выбор протокола

Межсерверные WireGuard и Hysteria2 на exit уже принимаются firewall только
от gateway; локальные управляющие входы слушают loopback. Межсерверный HY2
использует Salamander. Эти ограничения не делают IP невидимым и не скрывают
размеры или время передачи пакетов.

REALITY использует внешний TLS target при установлении соединения.
Доступность target нужно проверять отдельно. Изменение SNI, сертификата или
ключей нельзя выдавать за прозрачный server-only upgrade старого URI.
В частности, prerelease Xray 26.10.10 меняет требования к ClientHello;
установка поверх 26.3.27 без проверки реальных клиентов не допускается.

Другие варианты требуют отдельного сравнения:

| Вариант | Ограничение |
| --- | --- |
| HTTP/3 masquerade публичного HY2 | Не меняет его сертификат и не гарантирует нераспознаваемость; сам по себе не ускоряет трафик |
| AmneziaWG между серверами | Требует согласованного изменения двух концов; применять при доказанной проблеме распознавания WG |
| TUIC | Также зависит от UDP; не является независимым путём при общей блокировке UDP |
| NaiveProxy / ShadowTLS | Требуют нового клиентского профиля либо отдельной квалификации межсерверной передачи UDP |

Основной URI и версии компонентов в 0.23.7 сохранены. Новые протоколы
не включаются только потому, что опубликована более свежая версия.

Публичная веб-админка сохраняется. Её firewall-допуск по недавнему обращению
к VPN-порту **не подтверждает аутентификацию VPN-клиента**: сканер тоже может
отправить такой пакет. Ограничения и защищённый способ администрирования
описаны в [ADMIN.md](./ADMIN.md); полной защиты от сканеров здесь нет.

Источники: [REALITY закреплённой версии](https://github.com/XTLS/REALITY/blob/9234c772ba8f/tls.go),
[Hysteria 2](https://v2.hysteria.network/docs/developers/Protocol/),
[AmneziaWG](https://docs.amnezia.org/documentation/amnezia-wg/),
[TUIC v5](https://github.com/tuic-protocol/tuic/blob/master/SPEC.md),
[NaiveProxy](https://github.com/klzgrad/naiveproxy),
[ShadowTLS v3](https://github.com/ihciah/shadow-tls/blob/master/docs/protocol-v3-en.md).
